# v0.1.7：序章连续播放与渐进画质

## 问题与原因

「正在唤回下一段记忆…」表示下一张图尚未完成下载和解码。旧实现每次必须等到 236–449 KB 的原画才切幕，只准备紧邻的下一张，且与标题、岛屿图集共用两个加载位置。进入序章时还预取十种正文音效；请求最后一幕时立即预取海岸资源。这些开销在慢网下叠加，快速手动翻页更容易逐幕等待。声音本身不是画面就绪条件，但并行下载仍占带宽。

## 实现

1. 从现有原画生成八张轻量 WebP：最长边 768 px，完整构图不裁切，横屏 768×432、竖屏 512×768。`scripts/build-prologue-previews.py` 可复现，原始横屏 1672×941／竖屏 1024×1536 文件保留。
2. 横屏四幕首显共 171,074 字节，竖屏共 229,820 字节，比各自原画总量减少约 87%／85%。每张首显 32,784–65,246 字节。
3. 标题页只预热即将进入的序章画面。序章当前图有独立的直接加载路径，不等待正文图集队列；成功后依次准备剩余镜头的轻量图，再尝试当前幕的高清图。离开或旋屏后，旧加载完成可以留在缓存，但不会覆盖当前画面，也不会继续启动旧序列。
4. 升级清晰度保持镜头身份、节点、时间和声音状态，不再执行一次切幕动画。失败只保留已可用画面；如果轻量文件缺失，则原画可独立恢复。首显单次超时 8 秒，高清 12 秒，超时清理图片请求；失败显示重试入口，仍有退回、跳过和恢复网络后的重试。
5. 正文音效延后到登岛。序章仍播放当前音景，提前准备本幕猫叫／刻符揭示音效；最终海岸预取要等潮线画面已可见。

## 验证

浏览器脚本：`CHROMIUM_PATH=/usr/bin/chromium npm run test:prologue-loading`。清空浏览器缓存，在导航前施加 1 Mbps 下行与 150 ms 延迟，分别使用 1440×900 和 390×844。每幕仅停留 1 秒就翻页，比正常 9–10 秒连播更苛刻。计时从真实点击事件到目标幕解码就绪，不计 Playwright 等待字体／按钮布局的时间；原始资源耗时、截图和测量值保存在 `artifacts/prologue-loading/`。

2026-11-15 实测（秒，按四幕顺序；旧版为干净的 v0.1.6 / `216a41a` 发布包）：

| 视口 | 旧版 | v0.1.7 |
| --- | --- | --- |
| 电脑 1440×900 | 5.49 / 2.32 / 3.30 / 6.41 | 1.45 / 0.05 / 0.06 / 0.02 |
| 手机 390×844 | 5.83 / 2.81 / 3.80 / 7.31 | 1.30 / 0.11 / 0.79 / 1.29 |

测量是本地 Chromium 的网络模拟，不代表用户到阿里云的实际速度。断网时新图仍无法下载，首次打开整个应用的脚本／字体下载也没有被这次优化消除；已显示的轻量画面不会因高清失败而消失。

专项还覆盖：高清请求悬挂时依然播放；高清替换时播放进度不倒退；分别阻断轻量或高清文件仍能走完四幕。原有序章回归继续覆盖两档都失败后重试、横竖屏、回看、键盘、静音、暂停、跳过、存档恢复及登岛交接。单元测试覆盖共享请求、失败不缓存、过期结果、图片体积预算和正文声音延迟加载。

## 发布

从修复分支干净提交打包整个站点，替换 `/test/` 的 HTML、assets 和 version.json；不能只覆盖原有四张图，因为新 JS 需要八张带哈希的首显资源。存档键、格式与主线进度均不变。
